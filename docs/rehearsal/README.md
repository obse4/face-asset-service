# L0→L1→L2 贯通演练（episode_008）

**目的**：P0（帧级统一时间轴）与人脸服务此前各自验收过，但**从未一起用过**。本演练把两者接起来，
用真实素材跑一遍完整链路，验证"地基"确实能承重，并顺手补上此前记录的两个未验证项。

```
L0 时间轴  episode_008.timeline.json（26 镜头 / 2251 帧 / 30fps）
   ↓ 按部署方案 §4.1 的抽帧策略「确定性」推导帧号
L1 抽帧    42 帧 = 26 个镜头起点 + 16 个长镜头每 2.5s 补采（对比 naive 1fps 的 75 帧，省 44%）
   ↓ HTTP /analyze
L2 人脸    27/42 帧通过质量门控 → 检测 + 对齐 + 512d embedding + 质量分
   ↓ 锚点法归并
候选角色   3 个候选（≥2 帧）+ 2 帧转入人工复核队列
```

## 一、跑法与产物

```bash
python3 rehearse_pipeline.py --base-url http://192.168.9.21:8783 --api-key <key> \
    --timeline <episode_008.timeline.json> \
    --frames-dir <本机帧目录> --server-frames-dir <服务端帧目录> \
    --out <输出目录>
```

> 注意 `--frames-dir` 与 `--server-frames-dir` 的区别：服务在**远端**读文件，
> 所以发给它的必须是**服务端可见路径**。第一次跑就因为只传了本机路径而拿到 400。
> 该 400 的诊断体本来就有中文原因，脚本已改为把它一并抛出，避免误判成请求格式问题。

| 产物 | 内容 |
|---|---|
| `evidence/candidate_characters.json` | 候选角色分组（锚点、成员、质量、阈值、方法说明、单链接对照） |
| `evidence/frame_faces.json` | 逐帧人脸明细（帧号 → 镜头号、质量、face_px、置信、face_key） |
| `evidence/sampling_plan.json` | 抽帧计划（帧号 + 策略参数），**可复现** |
| `evidence/anchor_*.png` | 真值锚点帧（人工复核用；本仓库只保留 JSON，PNG 见部署项目） |

## 二、结果：三个候选角色恰好对应剧里三位真实角色

锚点法（阈值 0.35）输出 3 个 ≥2 帧的候选，**经肉眼逐帧确认真值**：

| 候选 | 锚点帧 | 锚点质量 | 成员 | 真值（人工确认） |
|---|---|---|---|---|
| `cand_01` | 1879 | 0.8466 | 5 帧（1879, 2104, 1954, 2029, 1773） | **老人** |
| `cand_02` | 259 | 0.6743 | 15 帧（259, 943, 868, 345, 184, 123, 1205, 1194, …） | **青年男主** |
| `cand_03` | 643 | 0.6666 | 5 帧（643, 1015, 718, 1804, 1355） | **女性角色** |

**这直接验证了锚点法的价值**：老人那组里的 1773 是 3/4 侧脸、1879 是正面清晰照，
两者余弦仅 **+0.650**——而此前正是这一类"同一人的不同视角"让**单链接与平均链接双双失败**
（部署方案 §4.3）。本演练中单链接的输出是"4 类、最大类 16 帧"，即把角色混在了一起。

对照：青年组 345（特写）对锚点 259 的余弦为 **+0.482**，正确归入。

## 三、发现的两种失效模式（都把结论落到了设计上）

### 1. "画面里的屏幕/监视器"——过了质量门控，但 embedding 无意义

帧 `1828` 是一台**监视器屏幕**的特写（还带故障条纹），里面同时有人脸。
它的质量分 0.5772**通过了门控**，但对老人是 +0.046、对青年是 +0.149 —— **与谁都不像**。

→ 检测器与质量分都拦不住它，因为它确实是"一张清晰的大脸"。必须靠**相似度兜底**：
与所有锚点都不够近时，**不能当成新角色**。（部署方案 §4.2 的门控是必要条件，不是充分条件。）

### 2. 阈值会漏并同一人

帧 `763`（青年与女性同框）对青年锚点的余弦是 **+0.326**，**卡在 0.35 阈值之下**。
它很可能就是青年本人（视角/光照不利），却会被判成"另一类"。

→ 单一全局阈值无法同时兼顾"不误并"与"不漏并"，尤其是本剧至少有三位角色时。

### 3. 由此产生的设计修正：孤类不自动成为新角色

原实现里，任何与现有锚点不够近的人脸都会**新建一个候选角色**。上述两种失效模式说明这样会
凭空"造"出角色。已改为：

> **只有 ≥2 帧相互支持的分组才成为候选角色；孤类进入 `review_queue`，连同"到最近锚点的分数"
> 一起交人工/LLM 确认。**

本演练中 `review_queue = [1828, 763]` —— 恰好就是上述两个问题帧。也就是说**该机制准确地把
不可自动判定的样本隔离了出来**，而不是污染角色表。

## 四、规模化验证（补上"未真跑整季"的缺口）

同一批 42 帧连续 20 轮 = **840 帧**（等效整季量级）：

```
合计 840 帧 / 46.58s = 持续 18.03 帧/秒
首轮 2.46s → 末轮 2.35s（无退化）
内存 485.7 → 486.1 MiB（+0.4MB，无泄漏迹象）
容器重启 0 次，健康状态 healthy
等效整季 800 帧 ≈ 44s
```

## 五、仍需人工/后续处理的事（不要误读本演练的结论）

- **候选 ≠ 身份**。三个候选分组只是"看起来是三个人"，**必须经人工确认并选定锚点图**之后，
  才能成为角色记录（这与 hypit 的做法一致：其文档明确人脸跟踪 id 不构成身份）。
- **`review_queue` 的两帧必须人工判定**（763 到底是不是青年、1828 该不该丢弃）。
- **仅一集样本**。跨集一致性尚未验证——那需要第二集素材，属于 L2 的下一步。
- **女性角色只出现 5 帧**：她在本集里戏份少，锚点质量 0.6666 也不是最高，
  跨集时需要为她单独确认锚点。
